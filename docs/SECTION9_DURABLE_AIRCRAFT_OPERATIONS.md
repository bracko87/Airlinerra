# Section 9 — durable, lease-fenced aircraft operations queue

## Implemented on 9 November 2026

This introduces an **engine-only** operational work queue for World 1. It is safe to install before launch: World 1 remains planned and the scheduling table is still constrained to `status='draft'` and `operationally_verified=false`.

### PostgreSQL
- `section9_aircraft_day_operations_jobs_v1` is a private RLS-enabled, revoked-from-browser table, with one unique job per (world, physical aircraft, game day).
- `section9_enqueue_aircraft_operations_batch_v1` only queues aircraft with **active + operationally verified** schedules, correct version-matched capacity and a signed game-day receipt. It uses bounded keyset pages of up to 200 aircraft. No browser-selected game clock can create work.
- `section9_claim_aircraft_operations_v1` claims queued work with `FOR UPDATE SKIP LOCKED`, a 3-minute token lease, and chronological blocking of newer days until older days complete.
- A **partial unique index on aircraft_inventory_id WHERE status='running'** prevents two active workers for the same aircraft even when they claim different dates.
- `section9_recover_expired_aircraft_jobs_v1`, `section9_heartbeat_aircraft_operations_v1`, `section9_fail_aircraft_operations_v1` manage expiry, 5 bounded attempts, exponential retry spacing, and terminal failure without skipping later days.
- **Critical fence:** `section9_record_leased_operated_flight_movement_v1` locks the job, checks live lease token/expiry, exact airline, physical aircraft and UTC event day, and calls the existing signed movement transaction *under the same database lock*. Expired or superseded workers cannot write movement events using the leased path.
- `section9_complete_aircraft_operations_v1` rechecks current signed game-day candidates and proves each expected movement exists in the authoritative physical movement ledger before marking the job complete. It cannot mark a non-operational draft as an operated flight.
- All functions use private `SECURITY INVOKER` access. No browser execution grants, no HTTP or Netlify route.

### Node server-only modules
- `section9-aircraft-operations-worker.mjs`: bounded, idempotent page enqueue; private claim, heartbeat, failure, completion and batch-run methods.
- `section9-verified-flight-operations-dispatcher.mjs`: an **optional lease mode** requires a heartbeat before each independent actual-operation decision and immediately before signed event ingestion.
- `section9-operated-flight-movement-ingress.mjs`: `acceptSignedLeasedFlightEvent(event, lease)` validates the existing flight-operation HMAC and calls the fenced SQL function in one statement. The old unleased adapter remains for compatibility but must not be used for the durable queue.

### Verification
- Rollback-only SQL acceptance tested: unopened world cannot enqueue, drafts do not enqueue, one running job per physical aircraft, earlier days block newer days, wrong/stale lease rejected, expiry recovery, retry and no movement/financial writes.
- Node tests cover safe queue handling, batched enqueue, 25,000-aircraft *pagination simulation* (not a database load or 500-player integration test), lease heartbeats, fenced signed-ingress SQL, recovery and fail-closed results.
- The PostgreSQL UUID pagination cursor was corrected in a separate follow-up migration after rollback testing found a missing `MAX(uuid)` aggregate.
- Neither the queue nor the new worker has a production Cron/HTTP integration or a trusted operations authorizer configured.

## Remaining blockers — do not claim real operations are complete

1. **Commercial activation release:** atomic certification of aircraft, all weekly rotations, crew duty/rest, permissions, slots, airport and flight restrictions, plus explicit engine-owned activation. Current draft-only constraints remain.
2. **Actual trusted flight-execution engine:** must produce durable, independently verified departure/arrival decisions; a scheduled candidate is not proof a flight operated.
3. **Deployment & recovery:** configure a private operations worker, real secrets and administration-controlled scheduling. Define late arrivals, cancellations, reassignments, cross-UTC-day delays, revocation and repair of terminal failed days.
4. **Bookings & finances:** precisely allocated passenger/cargo reservations and exactly-once airline revenue/expense settlement.
5. **Scalability:** database-level concurrency, chaos/retry and end-to-end load tests simulating 500 players with thousands of real operating legs. The 25k paging test is mock-only.

**Safety:** No flight activations, passenger bookings, aircraft positions or airline ledger rows are generated by the new queue installation.
